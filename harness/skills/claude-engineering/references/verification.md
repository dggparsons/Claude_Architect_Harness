## Corrections the harness must apply

1. **Refusals (row 2).** `stop_reason: "refusal"` arrives as a normal HTTP 200 response from Claude Fable 5.1, Fable 5, Opus 5.5, Opus 5, Sonnet 5.5 and Haiku 5.5, not only "Fable 5". Fable 5 is now a legacy model. Branch on `stop_reason` (not on `stop_details.category`, which can be `null`), log `stop_details`, and retry on a fallback model where appropriate.
2. **Forced tool use (row 6).** `tool_choice` is an object: `{"type": "any"}` or `{"type": "tool", "name": "..."}`. On Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, `any` and `tool` return a 400 error; on those models use `auto` with strict tool use or structured outputs. On any model, `any` and `tool` are not supported with manual extended thinking (`thinking: {type: "enabled"}`) and result in an error; there, use `auto` or `none`.
3. **`allowedTools` is not a delegation gate (rows 8, 9).** In the Agent SDK, `allowedTools` / `allowed_tools` only auto-approves tools; it does not restrict which tools exist. `Agent` needs no approval, so it runs whether or not it is listed, and leaving it out does not send spawns to `canUseTool`. What actually removes delegation: `disallowedTools` naming `Agent`, a `tools` list that leaves it out (for example agent frontmatter `tools`), or, for a coordinator that is itself a subagent, the spawn-depth limit `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (it counts layers below the main conversation, so it never removes delegation from the main agent).
4. **"Coordinator will not delegate" (row 10).** Anthropic's documented fix is in the prompt: name the subagent in the prompt and write a clear `description`. With the `claude_code` preset on Opus 5, Claude Code adds a line telling Claude not to call `Agent` unless asked. Remove any decision rule that prefers adding `Task`/`Agent` to `allowedTools` over prompt changes, and any reviewer checklist item that says the same, or reword them as "check `Agent` is not denied or missing from a restrictive `tools` list".
5. **Agent-to-agent communication (rows 14, 17).** Hub-and-spoke is the default, but it is not absolute in current Claude Code. Subagents with the `SendMessage` tool can message other named agents in the session, and agent-team teammates (experimental) message each other directly. Keep "route through the coordinator" as a design choice, not as a platform fact.
6. **SDK hook availability (row 18).** `PostCompact` is TypeScript-only in the Agent SDK. The Python SDK does not have it.
7. **SubagentStop has a `decision` field (row 25).** SubagentStop uses Stop-style decision control: `{"decision": "block", "reason": "..."}` keeps the subagent running and sends `reason` as its next instruction. Exit code 2 with stderr does the same. `hookSpecificOutput.additionalContext` also keeps the subagent running, but it shows as hook feedback rather than a hook error. To let the subagent stop, exit 0 with neither `decision` nor `additionalContext`. It is not an absolute gate: "after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn"; the count resets when Claude calls a tool, and `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` raises the cap (https://code.claude.com/docs/en/hooks, checked 2026-10-14).
8. **Hooks can rewrite tool results (row 26).** PostToolUse `hookSpecificOutput.updatedToolOutput` replaces what Claude sees for any tool, and the docs list no exception for `Agent`. It cannot undo side effects, and for built-in tools it is ignored if it does not match the tool's output shape. Drop the anti-pattern "any hook expected to rewrite a subagent's result". Instead, say that reshaping a subagent result in a PostToolUse hook is possible but hides the real output from Claude.
9. **Hooks and prompt injection (row 31).** Do not state that hooks "cannot be bypassed". The documented property is narrower: command hooks are deterministic, and a PreToolUse deny holds in every permission mode, including `bypassPermissions`. Known gaps: a typed `/skillname` skips PreToolUse (use UserPromptExpansion), a file changed through `Bash` skips an `Edit|Write` PostToolUse (use FileChanged), and `prompt`/`agent` hook types are model-judged. Test each hook.
10. **PostToolUse "block" does not stop the loop (row 38).** `decision: "block"` or exit 2 only adds feedback beside the result, and Claude continues. To halt, return `"continue": false`. Either way the side effect has already happened.

## Caveats on confirmed rows (worth carrying into the harness)

- `permissionDecision: "defer"` is honoured only in non-interactive `-p` runs. Interactive sessions log a warning and ignore it (row 19).
- The SDK `system:init` tools list still names the delegation tool `Task`, while `tool_use` blocks say `Agent`, so detection code should match both (row 7).
- Frontmatter `hooks` are ignored for plugin subagents. Project-subagent frontmatter hooks need workspace trust, and a `-p` session does not count as trust (row 27).
- `--continue` skips `-p`, Agent SDK and `/loop` sessions unless it is itself run with `-p` (row 34).
- In streaming, `stop_reason` is null in the `message_start` event (row 1).
- `model_context_window_exceeded` needs the beta header `model-context-window-exceeded-2025-08-26` on models older than Sonnet 4.5 (row 3).
- In a tool-result user message, the `tool_result` blocks must come first, before any text (row 5).

## Corrections the harness must apply

1. **Tool descriptions (#3):** Anthropic calls detailed descriptions "by far the most important factor in tool performance", with at least 3–4 sentences each. It does not say they matter more than names; it also recommends service-prefixed names (`github_list_prs`).
2. **Tool count (#4):** Anthropic's documented threshold is that selection "degrades once you exceed 30–50 available tools". Tool search is recommended from 10 or more tools. Keep "4–5 per agent" only as a labelled house heuristic, not an Anthropic figure.
3. **`tool_choice` modes (#5):** there are four modes: `auto` (default when tools are given), `any`, `tool`, `none` (default when no tools are given).
4. **`tool_choice` shape (#6):** always an object (`{"type": "any"}`), never a bare string (`"any"`).
5. **Forced tool use (#7):** `any` and `tool` return HTTP 400 on Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1. On those models, use `auto` plus `strict: true` for schema-valid tool inputs, or structured outputs for a fixed JSON reply. With manual extended thinking (`thinking: {type: "enabled"}`), on any model, `any` and `tool` are not supported and result in an error (the docs give no status code); use `auto` or `none`. Forcing a tool also skips thinking. Pick the mode in code per model; never hard-code forced `tool_choice`.
6. **Streamable HTTP (#13):** each message is an HTTP POST to one MCP endpoint, and the reply is either a JSON object or a request-scoped SSE stream, so SSE is optional. The old standalone SSE transport is deprecated in Claude Code.
7. **Client to server (#14):** each MCP client talks to exactly one server (1:1). One host runs many clients. The glossary's "one or more servers" is wrong.
8. **`CallToolResult` (#18):** in revision 2026-07-28 it has `content` (required), `structuredContent?` (any JSON value), `isError?` (default false), the inherited `resultType` (required from servers on this revision; `"complete"` for a final result, `"input_required"` when the server needs input; a client "MUST treat the absent field as `"complete"`" from an older server) and `_meta?`. Schema checks on tool results must allow `resultType` and `_meta`.
9. **Spec revision (#20):** cite `modelcontextprotocol.io/specification/2026-07-28/...` (or `/latest/`), not 2025-06-18.
10. **Error layers (#21):** argument and input-validation failures (wrong format, out of range) are tool execution errors. Return them as results with `isError: true` so the model can self-correct. Only unknown tools, requests that fail the `CallToolRequest` schema, and server errors are JSON-RPC protocol errors (`-32602` for an unknown tool).
11. **Example config (#26):** the GitHub URL `https://api.githubcopilot.com/mcp/` is confirmed. The Atlassian URL and the `server-filesystem` npx line are not in Anthropic's docs. Mark them unverified, or drop them from harness templates.
12. **Credentials (#27):** for remote (`http`) servers, put credentials in `headers` (for example `"Authorization": "Bearer ${GITHUB_MCP_PAT}"`). `env` only sets environment variables for a stdio server's process.
13. **Unset variables (#29), detail to add:** for a documented set of credential names (Claude Code's own such as `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`, cloud-provider ones such as `AWS_BEARER_TOKEN_BEDROCK`, and others such as `NPM_TOKEN` and `HTTPS_PROXY`), a remote server's `url` and `headers` expand them to empty with no warning, and `:-default` is ignored. Use your own variable names. An unset non-covered variable is passed through as the literal `${VAR}` text.
14. **MCP tool loading (#31):** tool search is on by default. MCP tools are deferred, and only tool names and server instructions load at session start; Claude finds the rest through `ToolSearch`. Servers connect in the background. To force upfront loading, use `alwaysLoad: true` per server in your configuration, or `ENABLE_TOOL_SEARCH=false`; a server author can set `_meta["anthropic/alwaysLoad"]: true` on one tool, and the user's server-level setting can override it. Tool search is off, and tools load upfront, with a non-first-party `ANTHROPIC_BASE_URL`, on models earlier than Opus 4 and Sonnet 4 (on Google Cloud's Agent Platform, earlier than Opus 4.5, Sonnet 4.5 and Haiku 4.5), and on Microsoft Foundry deployments hosted on Azure. By default (Claude Code v2.1.296 or later, checked 2026-10-14), server instructions and upfront-loaded tool descriptions are cut at 4,096 characters and deferred tool descriptions at 16,384 (before v2.1.296 the shorter limit was 2,048); tool search matches only within the shorter limit, and `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` replaces both limits. Put the key words first.
15. **Official remote servers (#34):** only GitHub's official remote server is confirmed in Anthropic's docs. The Atlassian claim is unverified.
16. **Built-in tools (#36):** Claude Code has far more than six built-in tools (the tools reference lists 46 rows, one marked removed), including `Agent`, `Skill`, `WebFetch`, `WebSearch`, `NotebookEdit`, `LSP`, `PowerShell`, `ToolSearch`, `ListMcpResourcesTool` and `ReadMcpResourceTool`.
17. **Grep and Glob (#37):** they are default tools only on Windows. On macOS, Linux and WSL, Claude searches with `find` and `grep` through Bash, which run embedded `bfs` and `ugrep`. Do not flag Bash `find`/`grep` as an anti-pattern on those platforms. Grep and Glob come back if you name them in `--tools`/`--allowedTools` or remove Bash. Hooks and permission rules see those searches as `Bash` calls.

1. **CLAUDE.md levels.** These are the levels, in load order: managed policy, then user `~/.claude/CLAUDE.md`, then project (`./CLAUDE.md` *or* `./.claude/CLAUDE.md`, one level, two possible places), then local `./CLAUDE.local.md`. `.claude/CLAUDE.md` and `CLAUDE.md` are not separate levels. (#2)
2. **`CLAUDE.local.md` is not ignored automatically.** Add it to `.gitignore` yourself (with `CLAUDE_CODE_NEW_INIT=1` set, `/init` does this when you choose the personal option). `.claude/settings.local.json` is ignored automatically only when Claude Code creates it; if you create it by hand, add it to `.gitignore`. (#8, #19)
3. **`@path` imports.** They work anywhere in the file, not only on their own line. A relative path resolves from the importing file. Imports nest at most four hops. A space in a path needs a backslash. Inside backticks or code fences, an import is ignored. (#10, #11)
4. **`paths:` in rules.** Write it as a YAML block list (`paths:` then `  - "glob"`). A comma-separated string also works. Do not rely on the inline `[...]` form, which no doc example uses. Bad YAML silently turns the rule into an always-on rule. (#25)
5. **After compaction,** project-root CLAUDE.md, unscoped rules and auto memory are re-injected. Path-scoped rules and nested CLAUDE.md files return only when a matching file is touched again. (#15)
6. **`/context` versus `/memory`.** `/context` lists the memory files loaded at launch. A subdirectory CLAUDE.md never appears there; it shows as a `Loaded` line in the terminal when it loads. A path-scoped rule shows the same way ("You see "Loaded .claude/rules/api-conventions.md" in your terminal, but not the rule content", context-window page). To log loads, use an `InstructionsLoaded` hook: its `load_reason` is `path_glob_match` for a path-scoped rule (hooks page; the memory page calls it "useful for debugging path-specific rules"). `/memory` lists locations and opens files, and it creates a file when you select one that does not exist yet. (#40, #63)
7. **Skill `description` fallback** is the first non-empty line of the body, not the first paragraph. (#22)
8. **`allowed-tools` and `disallowed-tools` last one turn only.** Both clear "when you send your next message". `disallowed-tools` is therefore not a lasting restriction. For a lasting restriction, use permission `deny` rules, or a subagent's `tools`/`disallowedTools`. (#59; skills page)
9. **`context: fork`** starts a subagent that does not see the conversation. Since v2.1.218 it runs in the background by default, with the narrower background tool set. Set `background: false` to wait for the result and keep the full tool set. `-p` runs always wait. (skills page, "Run skills in a subagent")

Explore and Plan start without CLAUDE.md, and so does any agent with `omitClaudeMd: true`; for all of them "a subdirectory's `CLAUDE.md` and matching path-scoped rules still load when the subagent works with files there". (sub-agents page)

12. **Settings precedence** runs: managed, then `--settings` on the command line, then `.claude/settings.local.json`, then `.claude/settings.json`, then `~/.claude/settings.json`. List keys such as `permissions.allow` combine across files instead of overriding. (#28, #29)
13. **`mcpServers` is not a `settings.json` key.** Team MCP servers go in `.mcp.json` at the project root. Local-scope servers (the default) and user-scope servers go in `~/.claude.json`. (#30)
14. **Hooks** have five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`) and about 30 events. They can be defined in settings files, plugin `hooks/hooks.json`, and skill or subagent frontmatter. Exit 2 blocks only on events that can block; PostToolUse cannot undo the tool call. Only `command` hooks are deterministic code: `prompt` and `agent` hooks "use a Claude model to evaluate conditions" (hooks-guide page). (#36–#38)

(#32) A `-p` run with no mode set can start in `auto`: "`auto` with Claude Code v2.1.285 or later" in sessions that don't fetch feature flags (for example a third-party provider or telemetry off). (permission-modes page, "Which mode a session starts in")
16. **`--bare`** also skips custom commands and subagents. It never reads OAuth or keychain credentials, so on the Anthropic API it needs `ANTHROPIC_API_KEY` or `apiKeyHelper`; Amazon Bedrock, Google Cloud's Agent Platform and Microsoft Foundry read their own provider credentials as usual. Skills from an `--add-dir` directory still load, but Claude is not given the skill list, so invoke them by name. It is planned to become the default for `-p`. (#45)

## Corrections the harness must apply

Current facts (2026-10-14) for every row not marked CONFIRMED:

1. **Schema guarantees (rows 1, 7, 8, 9, 11, 38, 39).** Plain `tool_use` with `input_schema` does **not** guarantee schema-valid input. Without `strict: true`, the model can send wrong types or leave out required fields. To guarantee conformance, set `strict: true` on the tool (grammar-constrained sampling) or use `output_config.format` for a JSON response. Strict mode needs `additionalProperties: false` on every object. It supports only a subset of JSON Schema. Its limits are 20 strict tools, 24 optional parameters and 16 union-type parameters per request. An unsupported feature returns 400. Even under strict, keep handling for `max_tokens` truncation, refusals and enum or `const` capitalisation drift, and keep the semantic validator layer. Structured outputs and strict tools are **not available on Claude in Amazon Bedrock** for any model (only the legacy Bedrock integration for Opus 4.6 and earlier has them): there, use prompt instructions or a non-strict tool and validate in code. The same applies to Claude Fable and Claude Mythos models in a CMEK organisation: "Structured outputs are not available for Claude Fable or Claude Mythos models in CMEK organizations." (https://platform.claude.com/docs/en/manage-claude/cmek, checked 2026-10-14).
2. **Forced `tool_choice` (rows 2, 4, 5, 11, 42, 43, 45).** There are four modes: `auto` (the default when tools are given), `any`, `tool` and `none` (the default when no tools are given). `any` and `tool` return **400** ("tool_choice: type \"tool\" and \"any\" are not supported for this model.") on **Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1**, including on the token counting endpoint. The Fable 5.1 and Mythos 5.1 guide also names the Message Batches API; for Opus 5.5 and Sonnet 5.5 the docs do not say, so do not send forced choices in batches. With manual extended thinking, on any model, `any` and `tool` "are not supported and result in an error" (no status code given; use `auto` or `none`). On the four models, the docs' replacement is `auto` plus `strict: true` plus a prompt instruction saying when to call the tool, or `output_config.format`. A mid-conversation `role: "system"` message naming the tool for the turn is another option (Fable 5.1 and Mythos 5.1 guide; the feature exists on all four models). Haiku 5.5, Opus 5, Sonnet 5 and older models still accept forcing (without manual extended thinking); a forced call there skips thinking. Where forcing is used, `any` + `strict` is the documented way to guarantee both a call and a valid schema. Even then, a response can end with `max_tokens` (an incomplete `tool_use`) or `refusal`, so do not assume `stop_reason == "tool_use"`.
3. **Schema syntax (rows 12, 14).** The docs do not say whether `nullable: true` or a per-property `required: true` is rejected or ignored. Treat both as lint errors anyway: use `"type": ["string","null"]` (counted in the union limit under strict) and a `required` array on the parent. Do not describe them as "rejected": whether these forms are rejected or ignored is untested; avoid both. Flatten nested schemas because deep nesting adds to grammar-compile complexity under strict. The docs say nothing about extraction accuracy.
4. **Model IDs (row 15).** Use current IDs: `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`, `claude-fable-5-1`. `claude-sonnet-5` is legacy (still available).
5. **Batch expiry and result types (rows 19, 24).** Expiry applies to each request. After 24 hours the batch's `processing_status` becomes `ended`. Unprocessed requests come back with `result.type: "expired"` (not billed), and finished requests keep their results. There are four result types: `succeeded`, `errored`, `canceled` and `expired`. Treat `errored`, `expired` and `canceled` as not done. Within `errored`, `invalid_request_error` needs the request fixed; other errors can be retried as they are. `processing_status` values: `in_progress`, `canceling`, `ended`.
6. **Tools in batches (rows 25, 26).** Batches accept tool use, multi-turn conversation histories, extended thinking and all server tools: web search, web fetch, code execution, MCP connectors, **advisor** and tool search. Server tools run their loop inside the batch item and can end with `pause_turn`; continue those in a follow-up request. Client tools end the item at `stop_reason: "tool_use"`, so a client-tool loop cannot complete inside one batch item.
7. **Other batch facts to encode (not claimed by the guide).** Batch limit: 100,000 requests or 256 MB. Results are available for 29 days after creation and come back in any order, so always join on `custom_id`. `custom_id` must match `^[a-zA-Z0-9_-]{1,64}$`. `stream: true`, `speed` (fast mode) and `max_tokens: 0` are not allowed in a batch. Each request's `params` are validated asynchronously, and errors appear only when the batch ends, so dry-run one request on the Messages API first.
8. **Prefill replacement (row 28).** Prefill is rejected on every current model. Replace it according to its purpose: for format, `output_config.format`, or a tool with an enum for classification; for a preamble, a system-prompt instruction; for a continuation, a user message; for a context reminder, the user turn. On Claude in Amazon Bedrock (any model), where structured outputs are not available, use prompt instructions plus validation in code. Older models still accept prefill: Opus 4.5, Haiku 4.5 (with thinking off) and the deprecated Sonnet 4.5.
9. **Sampling parameters (rows 29, 44).** For models released after Claude Opus 4.6: `top_k` with any value returns 400; `temperature` other than 1.0 returns 400; `top_p` below 0.99 returns 400 (on Haiku 5.5, any `top_p` other than exactly 0.99, including 1). On Haiku 5.5, sending both `temperature` and `top_p` returns 400. Separately, the Python SDK v1.0+ no longer defines the three parameters, so passing any of them, at any value, raises a `TypeError` (per the Opus 5.5 migration guide). Recommended: omit all three.
10. **System prompt placement (row 31).** The top-level `system` parameter remains the default. Mid-conversation `{"role": "system"}` messages now exist (no beta header) on Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 4.8, Opus 5, Sonnet 5.5 and Haiku 5.5, but **not Sonnet 5**. They override the top-level `system` field for the turns that follow them.
11. **Cost and caching (rows 32, 33).** An uncached system prompt is billed as regular input tokens on every call. Caching is opt-in: add top-level `cache_control` (automatic) or block-level breakpoints. It covers the `tools` → `system` → `messages` prefix and needs a minimum length (512 to 4,096 tokens by model). Cache reads cost 0.1× base input (0.05× on Opus 5.5 and Sonnet 5.5; 0.025× on Fable 5.1 and Mythos 5.1). Writes cost 1.25× (5-minute) or 2× (1-hour).
12. **Few-shot count (row 41).** Anthropic's guidance is "3–5 examples", wrapped in `<example>` / `<examples>` tags, relevant and diverse. The guide's "2 to 4" is narrower. Recommended harness default: 3 to 5.
13. **Unverifiable here (rows 34–37).** Confidence calibration and the exam facts are not in the API docs. Keep them tagged as guide or exam-guide claims, not API facts.

## Corrections the harness must apply

1. **Context-window sizes (claim 16).** Every current model is 1M tokens with 128K max output: Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5. The 1M window is the default and needs no beta header. Only older models are 200K, among them Haiku 4.5 and Sonnet 4.5 (deprecated). Replace "200K (Haiku 4.5) to 1M (Sonnet 5, Opus 5, Fable 5)" with this, dated 2026-10-14. The window covers input plus output, and cached tokens still count toward it. In Claude Code, Fable 5.1, Fable 5, Sonnet 5 and later, Haiku 5.5, and Opus 4.7 and later run at 1M by default. Opus 4.6 and Sonnet 4.6 reach 1M only through the `[1m]` variant, and access depends on the plan.
2. **System role (claim 8).** A `"role": "system"` message inside `messages` is now valid, with no beta header, on Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 4.8, Opus 5, Sonnet 5.5 and Haiku 5.5. It must immediately follow a user turn (including one carrying tool results) and must either end `messages` or be followed by an assistant turn; it cannot be the first entry, and one followed directly by another user message returns 400. It is not available on Sonnet 5. Remove "attempt to use a `"system"` role inside `messages`" as a blanket anti-pattern. The rule becomes: instructions that apply from the start go in top-level `system`; a mid-conversation system message is valid on supported models and does not invalidate the cached prefix before it.
3. **Context full (claim 5).** Replace "conversation history is lost" with the following. Claude Code auto-compacts near the limit. On native-1M models the default trigger is about 967K tokens; it can be set with `/autocompact`. Compaction replaces the conversation with a structured summary in which verbatim tool output and intermediate reasoning are lost. CLAUDE.md, auto memory, up to five of the files Claude read or edited (most recently modified first; a file over 5,000 tokens returns as a path only) and invoked skill bodies are reloaded. Manual `/compact` and auto-compaction work the same way ("The automatic pass works the same way as the `/compact` step"); a focused `/compact` keeps what you choose. Nested CLAUDE.md files and path-scoped rules are summarised away until their trigger file is touched again. On the raw API, an input that exceeds the window returns 400 "prompt is too long". The advice to keep findings in files still stands.
4. **Retry-After (claim 17).** Honour `retry-after` when it is present, but do not assume every 429 carries it. A Messages API 429 with `error.details.error_code == "enforced_spend_limit_reached"` (the monthly spend cap) has no `retry-after` and keeps failing until access resumes, so stop and report rather than retry. The official SDK already retries connection errors, 429s and 5xx errors twice with backoff by default (`max_retries` in Python; `maxRetries` in TypeScript). Do not stack a second unbounded retry loop on top of it.
5. **Usage fields (claim 15).** With prompt caching, `usage.input_tokens` counts only tokens after the last cache breakpoint. Total input = `cache_read_input_tokens + cache_creation_input_tokens + input_tokens`. Cost and context accounting must sum all three.
6. **Cache layout (claim 26).** The prefix order is `tools` → `system` → `messages`, so tool definitions go in `tools`, not `system`, and any change to them invalidates the whole cache.
